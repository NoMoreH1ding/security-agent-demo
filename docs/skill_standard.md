# Skills 知识库质量标准 v2.0

本文档定义了 `skills/` 目录下漏洞 PoC 文件的结构规范、质量要求和审核标准。所有新增或更新的技能文件必须遵循本规范。

---

## 1. 目录结构

```
skills/
  {component}/
    index.md              # 组件指纹 + 漏洞利用矩阵（必须）
    {CVE_ID}.md           # 单个漏洞 PoC（一个文件一个漏洞）
    {CVE_ID}.md
    ...
```

### 命名规则

| 元素 | 规则 | 示例 |
|------|------|------|
| 组件目录 | 小写字母 + 连字符 | `log4j`, `struts2`, `thinkphp` |
| CVE 文件 | 标准 CVE ID 或组件内标识 | `CVE-2021-44228.md`, `s2-046.md`, `ssti.md` |
| 索引文件 | 固定名称 `index.md` | `struts2/index.md` |

---

## 2. 索引文件规范 (`index.md`)

### 2.1 结构模板

```markdown
# {组件名称} 指纹与利用矩阵

## 组件特征
- 名称: {官方名称}
- 类型: {Java Web 框架 / PHP CMS / 中间件 / ...}
- 端口: {典型端口，多个用逗号分隔}
- 指纹: {关键识别特征，如响应头、Cookie 名、URL 路径特征}

## 漏洞利用矩阵
| CVE/ID | 类型 | 严重性 | 触发条件 |
| :--- | :--- | :--- | :--- |
| {ID} | {认证绕过/RCE/SQLi/...} | {Critical/High/Medium} | {一句话触发条件} |
```

### 2.2 硬性要求

- **索引必须与文件系统一致**：矩阵中的每个条目都有对应的 `{ID}.md` 文件；每个文件都在矩阵中有条目。两者数量必须相等。
- **严重性标准**：
  - `Critical` — 远程代码执行（RCE）、未授权访问
  - `High` — SQL 注入、认证绕过、文件上传
  - `Medium` — XSS、信息泄露、路径遍历
  - `Low` — 目录列表、版本泄露
- **指纹字段**不应为空，至少提供端口和一项识别特征。

## 3. 漏洞 PoC 文件规范 (`{CVE_ID}.md`)

### 3.1 完整结构模板

```markdown
# {漏洞名称} ({CVE-ID})

## 指纹特征
- 服务: {受影响的软件及版本范围}
- 端口: {典型端口}
- 关键特征: {一句话描述漏洞触发的前提条件}

## 利用矩阵
| 触发方式 | 路径 | 权限要求 |
| :--- | :--- | :--- |
| {GET/POST/Header/Payload 注入方式} | {URL 路径或触发入口} | {无 / 需登录 / 需特定权限} |

## 前置条件
- {如果有 JDK 版本限制、需登录、需特定配置等，在这里写明}
- {无前置条件则省略此节}

## 漏洞验证
{可选：无害的验证步骤，用于确认漏洞存在而不触发破坏性操作}

```http
GET /?name={{233*233}} HTTP/1.1
Host: {{TARGET}}:8000
```
*响应 Body 包含 `54289` 即确认存在。*

## PoC 指令

{漏洞利用的详细步骤}

### {方法一：XXX}

```http
{HTTP 请求原文，Method、Path、Headers、Body 必须完整}
```

{注意事项：如 payload 需要 URL 编码、特定编码方式等}

### {方法二：XXX（可选）}

{当有多个利用路径时，列出所有可行方法}

## 约束与限制
- {JDK 版本上限/下限}
- {需特定条件才能触发的场景}
- {不适用于某些环境的说明}

## Success Signal
- **{信号名称}**: {具体的可检测特征}（如 `响应 Body 包含字符串 "uid=0(root)"`）
- **{信号名称}**: {具体的可检测特征}

| 关键类/接口 | 说明 |
| :--- | :--- |
| {类名或方法名} | {一句话作用说明} |
```

### 3.2 各节字段要求

| 节 | 必须 | 说明 |
|----|------|------|
| 指纹特征 | 是 | 版本范围必须精确到小版本号，已知则写，未知写"版本号未知" |
| 利用矩阵 | 是 | 触发方式（Header/POST/参数/路径）、路径、权限要求 |
| 前置条件 | 否 | 如果漏洞有硬性约束（如 JDK ≤ 8u191），**必须**在此写明 |
| 漏洞验证 | 推荐 | 尽可能包含一个无害的验证步骤，如 `{{7*7}}` 或特征 Header |
| PoC 指令 | 是 | HTTP 请求原文必须 Method + Path + Headers + Body 完整，禁止缩写 |
| 约束与限制 | 推荐 | 版本限制、网络条件、依赖项等可能影响利用成功率的因素 |
| Success Signal | 是 | 至少一个具体的、可程序化检测的成功信号 |

## 4. 硬性规则

### 4.1 HTTP 请求格式

```http
POST /path/to/vuln HTTP/1.1
Host: {{TARGET}}:8080
Content-Type: application/x-www-form-urlencoded
X-Custom-Header: value

param1=value1&param2={{COMMAND}}
```

- Method、Path、Host 为**必填**
- `Content-Type` 在 POST/PUT/PATCH 请求中**必填**
- Body 与前一个 Header 之间**必须有空行**
- 禁止在 GET 请求中出现 `Content-Type`（除非 vulhub 明确包含）

### 4.2 变量占位符

| 占位符 | 含义 | 使用场景 |
|--------|------|---------|
| `{{TARGET}}` | 目标主机:端口 | 所有 Host 头、URL 中的目标地址 |
| `{{COMMAND}}` | 要执行的命令 | RCE 类 PoC |
| `{{ATTACKER_IP}}` | 攻击者监听 IP | 反弹 Shell、JNDI 等需要回连的场景 |
| `{{URL_ENCODED_PAYLOAD}}` | URL 编码后的完整 Payload | 需要编码的长 Payload |

- 禁止使用 `{{TARGET}}:8080` 硬编码端口，应统一用 `{{TARGET}}`（已包含端口信息）

### 4.3 Success Signal 规范

Success Signal 必须遵循**绝对化可检测**原则：

| 正确 ✅ | 错误 ❌ |
|---------|---------|
| 响应 Body 包含字符串 `uid=0(root)` | 看到命令回显 |
| 响应头中出现 `vulhub: 54289` | 返回异常 |
| 攻击机监听端口收到目标 IP 的 TCP 连接 | 目标会连接回来 |
| HTTP 状态码为 `200` 且 Body 长度 < 100 | 页面访问成功 |

所有信号必须统一使用以下三类术语之一：
- **结果回显** — 响应 Body 中包含特定字符串
- **状态验证** — 响应头/状态码出现特定特征
- **连接验证** — 网络层面收到回连请求

### 4.4 安全警告

所有产生破坏性操作的 PoC（RCE、文件写入、数据删除等）必须包含以下格式的警告：

> **安全警告**：该 PoC 会执行系统命令/修改目标文件/造成服务异常。仅用于授权测试环境。

### 4.5 编码说明

当 Payload 需要编码时，必须明确说明编码链路：

> **编码链路**：`OGNL Payload → URL Encode → 放入参数值`
> **编码链路**：`Java 序列化字节流 → AES/CBC/PKCS5Padding 加密 → Base64 → Cookie 值`

禁止只写"需要 URL 编码"而不给出编码后的示例。

## 5. 质量清单（提交前自检）

每条 PoC 提交前，逐项检查：

- [ ] **指纹精确**：版本范围已知则写精确，未知注明
- [ ] **前置条件完整**：JDK 版本限制、需登录状态、需特定配置等均已注明
- [ ] **验证步骤无害**：尽可能先提供无损验证再给利用步骤
- [ ] **HTTP 请求完整**：Method + Path + Headers + Body，无省略
- [ ] **`\x00` 等特殊字节**使用了正确方式表达（Python socket / 二进制写入），而非直接放入 HTTP 原文
- [ ] **多步利用的每一步完整**：不会出现"第一步做了 A，第二步假设 B 已就绪"的隐含依赖
- [ ] **编码链路明确**：若需编码，写明 `原始 → 编码A → 编码B` 的完整链路
- [ ] **Success Signal 绝对化**：是可程序化检测的具体特征，不是模糊描述
- [ ] **安全警告已添加**：RCE 类 PoC 必须有警告
- [ ] **索引同步**：`index.md` 已包含本条目，且索引总数与文件数一致

## 6. 常见问题（Avoid These）

| 问题 | 说明 | 示例 |
|------|------|------|
| 直接写 `\x00` 到 HTTP 头 | NUL 字节在文本 HTTP 中不可用，需用 Python socket 或二进制写入 | ❌ `filename="...\x00.jpg"` |
| 漏掉多步利用的前置步骤 | PoC 只写了最后一步，假设环境已经就绪 | ❌ WebFlow 漏洞省略了登录+订酒店流程 |
| 缺少版本约束 | 不同版本下 payload 可能不通用 | ❌ Log4Shell 不写 JDK 8u191 限制 |
| 未清沙箱直接调 `Runtime.exec` | Struts 2.5+ OGNL 沙箱拦截直接调用 | ❌ S2-059 缺少 `setExcludedClasses` 步骤 |
| 命令直接放 URL 路径 | 空格/引号在 URL 中需要编码 | ❌ 用 `echo hello` 替代 byte-array 编码 |
| 索引与目录不同步 | 新增 CVE 文件后未更新 index.md | ❌ struts2 索引只列了 10/20 个 CVE |

## 7. 审核标准（Review Checklist）

用于人工或自动化审查技能文件质量：

| 维度 | 权重 | 通过标准 |
|------|------|---------|
| 结构完整性 | 阻塞性 | 全部 7 个模板节齐全（含可选节合理取舍） |
| 可执行性 | 阻塞性 | 一个熟悉该领域的工程师可逐字复制成功 |
| 约束完整性 | 高 | 版本限制、JDK 限制、网络条件等全部标注 |
| Success Signal | 高 | 所有信号绝对化、可程序化检测 |
| 索引同步 | 阻塞性 | index.md 与文件系统一致 |
| 编码准确性 | 高 | 编码链路正确、命令经测试可行 |
| 安全警告 | 中 | RCE 类有警告 |
| 术语一致性 | 中 | Success Signal 使用三类标准术语之一 |

**审核结果**：
- **通过**：所有阻塞性项 + 至少 4 项非阻塞性项达标
- **有条件通过**：阻塞性项全部达标，非阻塞性项有 1-2 项不达标（需附加说明）
- **驳回**：任何一项阻塞性项不达标
